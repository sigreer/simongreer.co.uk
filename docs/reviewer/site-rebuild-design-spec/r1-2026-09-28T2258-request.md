  152	## 7. Contact form data flow
  153	
  154	1. `ContactForm.astro` renders `<form method="post" action={actions.contact}>` with name, email, message, a honeypot field, and the Turnstile widget (`TURNSTILE_SITE_KEY` from `astro:env/client`). Without JS the form posts and the page re-renders with the result; with JS the script calls `actions.contact(formData)` and updates an inline status region.
  155	2. `src/actions/index.ts` defines `contact` with `accept: 'form'`, Zod input: `name` 1–100 chars, `email` `.email()`, `message` 10–5000 chars, `website` (honeypot) must be empty, `cf-turnstile-response` string.
  156	3. Handler order: honeypot → `CONTACT_RATE_LIMIT.limit({ key: clientIp })` → Turnstile `siteverify` POST with `TURNSTILE_SECRET_KEY` and `remoteip` → build email → `EMAIL.send()` via `cloudflare:email` `EmailMessage` (from `CONTACT_FROM_EMAIL`, to `CONTACT_TO_EMAIL`, `Reply-To` set to the submitter). Returns `{ ok: true }`.
  157	4. Errors: each failure throws `ActionError` with codes `BAD_REQUEST` (validation), `TOO_MANY_REQUESTS`, `FORBIDDEN` (Turnstile), `INTERNAL_SERVER_ERROR` (email). The client shows a generic message for 500s and the specific message otherwise. Upstream error bodies are logged with `console.error` (structured JSON in Astro 7) and never returned to the client.
  158	5. Bindings are read from `Astro.locals.runtime.env`. In `astro dev` the adapter runs workerd with local bindings; `send_email` is stubbed locally by Wrangler (logs the message), and Turnstile uses the documented always-pass test keys.
